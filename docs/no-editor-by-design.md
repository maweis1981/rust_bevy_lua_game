# 我们没有编辑器，这不是欠账，是设计 —— 一篇反思

**—— 当"美术与视觉"不再需要视口：一个无编辑器游戏引擎为 AI 时代配备了什么，能输出什么，跑在哪里**

> 这是一篇反思式的 blog。它回答我们被问过最多的一个问题："你们的编辑器呢？"——并借这个问题，把我们为游戏美术与视觉真正配备的东西完整地摊开来讲一遍：每一件都有仓库里的代码背书，不是路线图上的愿望。

---

## 一、先承认：我们也动摇过

每次给人看这个项目——Rust + Bevy 做引擎层、Lua 写玩法、agent 做开发——对方的第一反应几乎总是同一句：

> "挺有意思。那……编辑器呢？"

说实话，我们动摇过。毕竟过去二十年，"游戏引擎"这个词在多数人心里就等于那个界面：左边场景树、中间视口、右边 Inspector、下面资源浏览器。Unity 是这样，Godot 是这样，Unreal 是这样，Cocos 也是这样。没有那个界面，你好意思叫引擎吗？

Bevy 社区被这个问题拷问了六年。"没有编辑器"常年排在 Bevy 质疑榜第一位，官方也确实在憋一个 editor preview。我们最初的想法也是"先欠着，以后补"。

直到我们真的用 agent 把八个游戏做出来之后才想明白：**对我们要的开发方式来说，编辑器不是还没建好的基础设施，而是一个负资产。"没有编辑器"不是我们的欠账，是我们的地基。**

这篇文章解释为什么——以及更重要的：不给编辑器，我们给美术和视觉配备了什么。

## 二、编辑器到底是什么？

剥掉情怀，编辑器的本质是一个 **I/O 适配器：把人类的手（鼠标、拖拽、滑块）接到场景数据上**。

它优化的是人的输入带宽。人不擅长在脑子里想象 `position: (312.5, -87.0)` 长什么样，所以需要拖一下、看一眼；人记不住四千个 API，所以需要 Inspector 把所有属性铺在面板上；人对不齐颜色，所以需要取色器。**编辑器的每一个控件，都是对"人类感官与肌肉"的一次妥协。** 这些妥协五十年来无比正确——因为操作者一直是人。

但代价也一直在账上，只是我们习惯了不看：

1. **场景文件是给机器读的，不是给人读的。** 二进制或半可读的 `.unity`/`.prefab`/`.tscn`，diff 不可读、merge 靠祈祷、review 靠"你打开引擎看一下"。
2. **视口会说谎。** editor 里的光照、缩放、导入设置和真机 build 永远差着一层，"在我的编辑器里是好的"是行业老梗。
3. **一致性靠纪律，不靠构造。** 风格指南写在 wiki 里，三个美术画出三种描边粗细；编辑器管得住坐标，管不住风格漂移。

当操作者从人变成 agent，这笔账就翻转了。agent 没有眼睛和手要伺候——它的原生 I/O 是**文本**。给 agent 一个 GUI，等于给鱼一辆自行车；而编辑器的三个隐性代价（不可 diff、视口谎言、纪律依赖），恰恰打在 agent 工作流的死穴上。

所以我们的选择是：**不去给 agent 造一个它用不了的界面，而是把编辑器的每一项职能，换成 agent 原生的形态。**

## 三、我们为美术与视觉配备了什么

编辑器有五项核心职能：定风格、管资产、摆内容、调参数、看效果。下面逐项对照，我们用什么替换了它——每一项都指向仓库里真实存在的文件。

### 1. 定风格：一份"可执行的风格圣经"（`tools/style_bible.py`）

传统流程里，美术总监的风格指南是一份 PDF；两周后有人在外包邮件里转述它，色板就开始漂移。我们把风格圣经写成了**代码**。它的文件头写着这套做法的动机：

> "A style bible's only job is to make every future asset look like it came from the same hand. The failure mode is drift… Encoding the locked tokens as data + a tiny assembler kills drift **by construction** — the shared DNA is literally the same string every time, and only the per-asset subject slot changes."
>
> （风格圣经唯一的职责，是让未来的每一张素材看起来出自同一只手。它的失败模式是漂移……把锁定的风格 token 编码成数据 + 一个小小的拼装器，就**在构造上**消灭了漂移——共享的 DNA 每次都是同一个字符串，唯一变化的只有每个素材的主体词。）

具体来说：色板（pastel 花园 kawaii 系）、描边规则、视角（3/4 俯视）、构图（居中留边）都是锁死的常量；每个素材只填一个"主体"槽位（"a cute shiny red apple with a small glossy green leaf"）。想换整个游戏的美术方向？改一个 `ACTIVE_PALETTE` 开关，全套素材按新极性重新生成。**风格一致性从"美术的自觉"变成了"程序的保证"——这是任何编辑器都做不到的事，因为编辑器约束的是坐标，不是审美。**

### 2. 管资产：一份声明式素材清单（`tools/floniks_manifest.json`）

美术资源在我们这里有"源代码"。清单里的一行就是一个素材的全部真相：

```json
{"name": "gem", "w": 16, "h": 16, "bg": "alpha",
 "subject": "a cute glowing teal diamond gem, faceted, glossy, bright cyan-teal core"}
```

名字、精确像素尺寸、抠底方式（透明棋盘格 / 纯蓝键控 / 纯黑保留辉光 / 满幅贴图四种模式）、主体描述。**素材不是"某次生成的产物"，而是"随时可以从清单重放的结果"。** 丢了？重跑。想全部提升到 2x 分辨率？改 `w/h` 重跑。这就是美术资产的 Infrastructure-as-Code。

### 3. 造资产：Floniks 生成管线（`tools/floniks_build.py` / `floniks_sprite.py` / `slice_sheet.py`）

清单的执行者是一条自动化管线，接在 [Floniks](https://floniks.com)（我们的 AIGC 平台，经由 MCP 调用）上：

```
风格圣经拼 prompt → Floniks 文生图（GPT-Image-2 等模型）
  → floniks_build.py 下载 → 按清单键控抠底（每种底色有标定好的容差表）
  → 精确缩放到目标像素尺寸 → 写入 assets/textures/
  → 同时输出 8x 最近邻放大的 preview 图供人眼快检
```

序列帧走 `slice_sheet.py`：生成一张 sprite sheet，按网格切成 `walk_0.png … walk_7.png`，Lua 里用 `game.set_sprite_image` 轮播——一个十行的帧计时器就是动画系统。工程细节也都沉淀在代码注释里（比如"GPT-Image-2 不理透明底请求，所以我们用纯色键控再抠"、"`size` 要传 `WxH` 而不是 `aspect_ratio`，否则 400"）——**踩过的坑变成了管线的一部分，而不是某个人的记忆。**

在此之下还有一层保底：`gen_textures.py` / `gen_audio.py` / `gen_sprites.py` 等纯标准库的程序化生成器，零依赖地产出全套占位素材。**游戏在任何时刻都是可跑的**，AI 素材是升级，不是依赖。

### 4. 摆内容与调参数：契约 + 热重载的 Lua

编辑器的场景树和 Inspector，我们用两样东西替换：

- **契约**。`ART_REQUESTS.md` 规定素材同名同尺寸即插即用；`tools/PACK_SPEC.md` 一页纸写清一个游戏包的全部约定（`make_<key>()` 工厂、`PACKS` 自注册、可用贴图清单、"必须暴露 `DEBUG` 表供无头测试驱动"）。菜单从 `PACKS` 自动生成——**没有任何一步需要在 GUI 里点。**
- **热重载**。所有摆放和参数就是 Lua 源码里的数字，而 Lua、贴图、甚至 WGSL shader 都走 Bevy 资产管线，桌面端保存即生效。想调苹果下落的速度？改数字，保存，屏幕上立刻变。**Inspector 的滑块被"文本 + 秒级反馈"替换了**——对人不差，对 agent 是唯一可用的形态。

### 5. 看效果：运行中的游戏本身就是视口

我们没有"编辑器视口"，因为**预览窗口就是正在运行的游戏进程本身**——所见即所得的终极形式：没有导入设置差异，没有 editor 光照与 build 光照之别，你看到的每一帧就是玩家将看到的那一帧。配合运行时视觉 API，视觉表现力并不寒酸：

- `set_color` 染色系统：灰度贴图 + 运行时染色，一张图变一族图（球的红绿状态、消除时的闪白）；
- `set_rotation` / `set_size` / `set_sprite_image`：旋转、缩放、换帧动画；
- 全屏 **WGSL 自定义 shader** 背景：域扭曲分形噪声的极光，且**随玩法呼吸**——每个游戏的 `game.shake` 打击反馈同时驱动背景的能量值，命中越猛烈背景越亮、流速越快，零 Lua 代码、跨所有游戏生效；`set_bg_theme` 一行切换主题色相;
- 屏幕震动（trauma² 衰减模型）、四档触觉反馈、合成音效/循环 BGM——"juice"三件套齐全。

而验收不靠眼睛盯：677 行的无头不变量套件把"手感"写成断言（不穿模、不瞬移、速度有上限、绿球命中必有音效和震动），`make test` 就是 agent 的眼睛。**编辑器让人看见，测试让 agent 看见。**

## 四、为什么说这套东西"超越"了编辑器

把上面五件拼起来，会得到几个编辑器在原理上给不了的能力：

1. **美术可以整体重生成。** 风格圣经改一个 token → 清单重放 → 整套素材在一小时内换新且彼此一致。在编辑器流程里，这叫"美术返工三周"。
2. **美术可以被 code review。** 一次美术改动的 PR = 清单 diff + preview 截图，可以回滚、可以 blame、可以在评论区逐行争论"这个描边是不是太粗"。二进制场景文件永远给不了这个。
3. **一致性是构造出来的，不是要求出来的。** 同一条 prompt DNA、同一张容差表、同一个像素化管线——不存在"新来的美术不知道规范"。
4. **玩法与美术在同一个循环里。** 同一个 agent、同一次会话：改玩法 Lua → 发现需要新素材 → 调 Floniks 生成 → 按契约落位 → 热重载看效果 → 跑测试 → 提交。在传统管线里这是两个部门 + 一个导入流程 + 一次会议。
5. **对话即编辑器。** "把苹果画得更红、光泽更明显一点"——这句话就是一次完整的编辑操作：agent 改清单里的 subject，重放管线，热重载给你看。编辑器把操作映射到鼠标轨迹，我们把操作映射到自然语言。**后者的表达力上限显然更高。**

也要诚实地写下代价：**这套流程假设操作者是"一个人 + agent"。** 一个不写代码、也不想通过 agent 工作的传统美术或关卡策划，今天在我们这里无处下手；需要人手精摆几百个物件的关卡类型（解谜关、平台跳跃关）目前也没有顺手的工具（答案大概率是"关卡即数据 + agent 生成 + 测试验证"，但我们还没做到，不吹）。编辑器五十年的人体工学积累是真实的——我们不是说它错了，是说**它优化的对象（人的手）不再是我们工作流里的瓶颈**。

## 五、我们能输出什么形式

盘点当前管线端到端支持的视觉/听觉产出形态（全部有代码与在库素材背书）：

| 形式 | 管线 | 状态 |
|---|---|---|
| 透明底静态 sprite（角色/道具/图标） | Floniks 生成 → 键控抠底 → 精确像素尺寸 | ✅ 在用（约 60 张在库） |
| 可染色灰度贴图（一图多色） | 同上 + 运行时 `set_color` | ✅ 在用 |
| 序列帧动画 | sprite sheet → `slice_sheet.py` 切片 → `set_sprite_image` 轮播 | ✅ 管线在，帧动画已可跑 |
| 全屏背景 / 竞技场场景图 | Floniks 竖幅生成（1024×1536）→ 满幅模式 | ✅ 在用（花园/沙滩/寿司屋等） |
| UI 素材（按钮/装饰件） | 同 sprite 管线（`gen_ui_art.py` 打底） | ✅ 在用 |
| 程序化动态背景 | 手写 WGSL（域扭曲 FBM 极光），玩法联动 | ✅ 在用，热重载 |
| 音效 / 循环 BGM | `gen_audio.py` 合成 WAV（Floniks 文生音乐是下一步） | ✅ 在用 |
| 字体 | TTF 直接落 `assets/fonts/`（当前 Latin，CJK 待配） | ✅ 在用 |
| 宣传物料（截图/预告片） | 截图已入库；Floniks 图生视频可产预告片 | 🔶 截图 ✅，预告片是能力但未进管线 |

暂不支持的形态（诚实清单）：骨骼动画（Spine 类）、粒子系统、tilemap、法线/光照贴图、3D。前三个都有明确的 Bevy 生态方案，缺的只是往桥上开洞。

## 六、跨平台吗？

分三层回答，不含糊：

**素材层：100% 跨平台，且无锁定。** 我们的全部资产是 PNG、WAV、TTF、WGSL、Lua、JSON——没有专有场景格式，没有编辑器工程文件，没有导入数据库。WGSL 经 naga 编译到 Metal / Vulkan / DX12 / WebGPU，天然全平台。**你今天决定弃用我们，素材原封不动搬去任何引擎。** 这是无编辑器架构附送的自由。

**引擎层（Bevy）：桌面三平台 + Android + iOS + Web（WASM/WebGPU）都有官方支持。** 命令队列桥的语义与平台无关。

**本项目已接通的：macOS（开发环境，热重载）+ iOS（模拟器与真机，Metal，120Hz ProMotion，自动签名，TestFlight 管线已合并）。** 同一个 Rust crate 编成桌面 `rlib` 和 iOS `staticlib`，没有两套代码。Android 和 Web 是路线图：引擎无障碍，工作量在打包管线（NDK / WASM 构建脚本），属于 agent 可以按清单执行的体力活，而非架构风险。

## 七、结语：编辑器没有消失，它换了形态

反思到最后，我们的结论不是"编辑器已死"。编辑器承担的职能——定风格、管资产、摆内容、调参数、看效果——一项都没有消失，它们只是各自找到了 agent 原生的新形态：

| 编辑器的职能 | 我们的形态 |
|---|---|
| 风格指南 PDF | 可执行的风格圣经（锁死的 prompt DNA） |
| 资源浏览器 / 导入设置 | 声明式清单 + 可重放的生成管线 |
| 场景树 / 拖拽摆放 | 契约（PACK_SPEC / ART_REQUESTS）+ 自注册 |
| Inspector 滑块 | 热重载的 Lua 源码 |
| 编辑器视口 | 运行中的游戏本身 + 无头测试 |
| 鼠标操作 | 自然语言对话 |

五十年来，游戏工具的每一次进化都在回答同一个问题："怎么让创作者的意图更快地变成屏幕上的画面？"当创作者身边多了一个 agent，这个问题的最优解就不再经过 GUI。**我们不是没来得及做编辑器——我们是把做编辑器的力气，花在了让"说一句话"成为最短路径上。**

这条路对不对，仓库里的八个游戏、六十张 AI 生成的在库素材、和一台跑着 120Hz 的 iPhone 会继续替我们回答。
